# AGENTS.md

Django 5.2 (Python 3.13) timetable app for COET. The only active app is `core`; `allocation` is a stub (empty models, no migration). Project templates live in `templates/` (global `DIRS`) with shared partials under `templates/core/`.

## Commands

All from repo root (`E:\COET_TIMETABLE\Coet_timetable`). Use `.venv\Scripts\python.exe` — a second venv `venv/` also exists, both Python 3.13.

- Dev server: `.venv\Scripts\python.exe manage.py runserver`
- Sample data import requires `--file` (README omits the flags), and order matters:
  ```
  manage.py import_semesters --file sample_data/semesters.xlsx
  manage.py import_programmes --file sample_data/programmes.xlsx
  manage.py import_student_groups --file sample_data/student_groups.xlsx
  manage.py import_programme_courses --file sample_data/programme_courses.xlsx
  manage.py import_venues --file sample_data/venues.xlsx
  manage.py import_master_timetable --file sample_data/master_timetable.xlsx --semester 1
  manage.py import_workshop_allocation --file sample_data/workshop_allocation.xlsx --semester 1
  manage.py import_td_allocation --file sample_data/td_allocation.xlsx --semester 1
  ```
  `create_sample_data.py` regenerates those Excel files and prints the full command sequence. Import commands `exit(1)` on any row error. Master-timetable imports require `--semester` (the PK of the target `Semester` — it is never auto-created) and support a `--dry-run` flag (reconcilies/validates but writes nothing; also prints `DRY RUN — no records were written.`). `import_programme_courses` also takes `--requirements-column "<exact header>"` to point at the requirements column when the heading is spelled in a way the importer cannot guess.
- `manage.py set_course_requirements (--file <path> | --from-sessions) [--requirements-column H] [--dry-run]` — set the required activities of courses that **already exist**, from a two-column sheet (`course_code` + `Required Activities`, same rules as the import) or derived from the timetable. It never creates a course and never touches programme links or sessions. A blank cell in a `--file` row *is* a statement ("needs nothing") and is reported as `CLEARED` when it removes an existing requirement, so run `--dry-run` first. Unknown course codes are reported, not created.
- **The order matters for requirements**: a course requirement needs *both* the course and its sessions to exist, so the derivation can only run after the programme-course and master-timetable imports.
- Test suite: `.venv\Scripts\python.exe manage.py test` runs 552 tests in `core/tests.py` (import reconciliation/idempotency, adaptive alias/reshape imports, CSRF-enforced CRUD responses for htmx and plain posts, sidebar active-nav, upload view, PDF/timetable exports, the group allocator, and requirement parsing/column detection/derivation). Uses an isolated test DB — `db.sqlite3` is never touched. Keep uses of `make_xlsx` (module function) rather than a per-instance `_xlsx`.
- `manage.py check_course_requirements [--semester N]` — read-only report of courses with no required activities configured and of course codes that were imported under several different names. `sys.exit(1)` when anything needs attention.

## Conventions when adding features

- CRUD is hand-rolled and repetitive in `core/views.py`: one resource = list + create + edit + delete + detail views, 5 URL patterns (`core/urls.py`), and templates. Copy an existing block (e.g. venues) instead of writing class-based views.
- List views filter on `?q=` plus resource-specific filters, and render the partial `core/_table_and_cards.html` when the `HX-Request` header is present, otherwise the full `core/list.html`.
- Write views return `HttpResponse("")` with an `HX-Trigger` header on success (`close-modal,refresh-table`, plus `refresh-detail` for edits) via the shared `_write_response(request, trigger, redirect_name, *args)` helper, which also does a plain `redirect()` for non-htmx POSTs so saves never appear to hang. The browser modal/slide-panel JS in `templates/base.html` is wired to those triggers and auto-refreshes — keep using them.
- Every mutating view (create/edit/delete for the 8 CRUD resources, session group add/remove/clear, lecture-group assignment, import uploads) records an `ActivityLog` entry via the `_log(action, message, resource="", target="")` helper in `core/views.py` (uses `LogAction` choices). Keep logging in any new mutating view. The sidebar's Activity Log section renders the latest entries via the `{% activity_logs N as logs %}` tag and `log_badge_cls` filter in `templates/partials/sidebar.html`; each entry links to the dashboard with `?log=<pk>`, and `dashboard()` reads `request.GET["log"]` to display it in a dismissible panel whose Cancel button links back to the bare dashboard (no `?log=`).
- Frontend is htmx (2.0.4) + Alpine.js + Tailwind, all loaded from CDNs (requires internet, no bundler). Form templates post with `hx-target="#modal-content"`. After innerHTML swaps, `base.html` runs `Alpine.initTree` on the swapped element (via `htmx:afterSwap`) — page-level Alpine state lives on `<body x-data>` so it must be hoisted there, not on a swappable child. Sidebar active state comes from the `nav_section`/`active_cls` tags in `core_tags.py` (derived from `request.resolver_match.url_name`); per-view `NAV` context keys no longer exist.
- **The staff app matches the student portal's mobile feel, deliberately.** Four things carry that, and all are asserted in `SidebarStructureTests` so they cannot quietly regress:
  - **A tap is tinted, never flashed.** `base.html` sets `-webkit-tap-highlight-color` to a translucent app blue on links/buttons/`summary`/`label`/`[tabindex]`, so a phone tap reads as deliberate rather than as the browser's own grey-blue box. **The dark chrome cannot carry the app blue** (sidebar, top bar, mobile bottom nav sit on navy), so it gets a light `rgba(255,255,255,.16)` wash instead, and `input, textarea, select` are exempt — a tint over a field being typed into is noise. Do not "simplify" this into one global colour.
  - **`:active` is paired with `:hover` on the themed palette overrides.** Tailwind's `hover:*` is the only state a tap produces, so each themed `body [class~="hover:bg-…"]:hover` rule in `base.html` repeats with `:active`; without it the press colour vanishes the moment the finger lifts and only the flash is left. When you add a themed hover override, add the `:active` half in the same edit.
  - **The browser's own chrome is the app's colour, not white.** The OS paints the URL/status bar, so this is requested, not styled: `base.html` carries `theme-color` **plus the `prefers-color-scheme` light *and* dark variants** (one untagged tag is a *white* bar on a dark-mode phone), and the standalone tags `mobile-web-app-capable` / `apple-mobile-web-app-capable` / `apple-mobile-web-app-title`. `apple-mobile-web-app-status-bar-style=black-translucent` only does anything alongside `viewport-fit=cover` — the pair is what removes the pale strip, and both are asserted together for that reason. The area above the document is `<html>`, not `<body>`, so `html { background: var(--coet-blue-dark) }` is what colours the rubber-band region; body's own `--coet-canvas` still paints the page.
  - **The phone top bar is the portal's height, and its height is a `calc()` — never a `h-*` utility.** `body .topbar` is `calc(4.25rem + env(safe-area-inset-top))` (5rem at `sm`, 4.5rem at `lg`), where 4.25rem is the portal's own bar (`.7rem` padding around a `2.8rem` menu) — tapping through from the portal must not feel like the app shrank. The inset is why it is CSS: the bar has to *grow* by the notch and push its content down, and only a `calc()` can do both. **Re-adding `h-[4.25rem] sm:h-20 lg:h-[4.5rem]` to the `<header>` is a second source of truth for one box and silently drops the inset** — the test asserts both that the classes are absent and that the rule is present. The rules are `body`-prefixed to outrank the Tailwind CDN's runtime-injected utilities at equal specificity. The bar is `sticky`, not fixed, so nothing needs a matching top offset.

### Navigation, loader and the issue bell

`templates/partials/sidebar.html` groups the links into exactly three **collapsible** sections — Reference Data, Timetable, Allocation — and leaves Data Import, Export and Activity Log flat. Anything that gets its own section header must be added to `SECTION_KEYS` in the `sidebar` Alpine store in `base.html`; a header is useless otherwise, because the section body is `x-show`-bound to that same key.

- **Collapsed sections are not "hidden" on a collapsed desktop sidebar.** `isSectionDivider()` is true whenever `collapsed && isDesktop`, and it short-circuits `isSectionOpen` to `true` and disables the header button. That is what makes a narrow sidebar show the child *icons* while each header collapses to a 1px full-width rule, instead of hiding the child pages. Do not make `isSectionOpen` respect `sections[key]` on desktop-collapsed, or the icon-only rail loses its items.
- **The rule colour is set by the active section.** `html.tt-collapsed #app-sidebar .tt-section` uses `color: transparent` (one selector *type* more than `#app-sidebar .tt-section.is-active`), so an active section's header still gets the cream accent; the hover rule is scoped `:not(:disabled)` so a divider can never light up on hover.
- Section open/closed state persists in `localStorage` under `coet.sidebar.sections`. `isDesktop` is initialised from `matchMedia('(min-width: 1024px)')` and refreshed on `resize` in the store's `init()` — without that, a page loaded on a phone would treat the mobile drawer as the desktop collapsed rail and render every header as a divider.
- Adding a link to a section also means adding its `nav` key to that section header's `{% nav|nav_is_any:'...' %}` list (`nav_is_any` in `core_tags.py`), or the header won't highlight on that page. Both programme-course and shared-course links use the `courses` key, so a new section header must list every child key it covers, not just the first.
- **`#page-loader` in `base.html` is for full-document navigations only.** Its JS skips a submit when `htmxDriven(form)` is true, so htmx writes never flash the overlay; `beforeunload`/`load`/`pageshow` are the catch-all for plain posts, `form.submit()` calls and back/forward restores. Hide on `htmx:afterRequest` too, or a failed htmx request that started from a real navigation leaves it stuck.
- **An Alpine busy flag must be cleared by the request that set it.** The upload form in `core/import_upload.html` sets `uploading = true` on `@submit` and clears it on `@htmx:after-request.window`, filtered to its own element (`$event.detail.elt === $el`). The result panel arrives as a swap, so nothing else on the page can end that state — a flag only reset by a reload leaves the button disabled and reading "Importing…" on top of a finished import. `htmx:afterRequest` is the one event that always ends a request (success, error or abort), so use it rather than `afterSwap`. The `.htmx-indicator` panel in `#upload-result` needs no such care: htmx owns `htmx-request` and drops the class itself.
- **The current semester is `Semester.is_current`**, set from the semesters list at `/semesters/` — a per-row **Make current** / **Unset current** button (`core/urls.py` name `semester-set-current`, view `semester_set_current`, POST only) plus the `core/_semester_current.html` panel above the table. It is a **single value, and the database enforces it**: `core/models.py` carries a conditional `UniqueConstraint` on `is_current=True` (`core_semester_only_one_current`), so a page can never read two "current" terms. Always write it through `Semester.set_current(semester_or_None)`, which clears every other row in one transaction; the admin changelist ticks the boolean directly and `SemesterAdmin.save_model` clears the previous holder for that reason. The label states the *action*, never the state, so a second tap cannot silently unset the term the app is working in.
  - Readers, in precedence order: the **portal override** `student_portal.PortalSettings.current_semester` (a required-field singleton, so creating a row is deliberate), then `Semester.current()`, then the newest semester. `dashboard()` uses that chain for a bare visit; `_latest_semester_with_data()` honours the current semester **only when it holds data**, because a term marked current before anything was imported into it would otherwise make the exports print a blank sheet. `import_upload()` preselects it. The remaining pickers (timetable, allocation, exports) stay per-view `?semester=` filters.
- **`Semester.current()` is a plain manager call, not a related-name lookup.** The admin's `is_current` column is a convenience, not the second write path.
- **The bell counts `CollisionReport` rows that are not `Status.RESOLVED`.** The count comes from the `issue_notifications` context processor in `core/context_processors.py` (registered in `coet/settings.py`), *not* from a view, so every page renders it. It swallows `DatabaseError`/`ImportError`/`AttributeError` and falls back to 0 rather than taking a page down. The label is a pluralised `N reported issue(s) awaiting review`; don't hardcode a singular form.
- **The wordmark is one partial, and the top bar wears it only on the dashboard.** `templates/partials/brand.html` is the sole statement of the brand ("CoET" in `tt-brand-accent` cream, "Timetable" in white); the sidebar rail and the top bar both `{% include %}` it, and `brand_size` is the only thing a caller may pass. The top bar swaps its `page_title` `h1` for the wordmark when `nav_section` is `dashboard` — on the front door "Dashboard" says nothing the user cannot see, and it was the one place the wordmark was missing. Everywhere else the bar still names the page, because a brand in the bar on every screen leaves no way to tell where you are. It is a **link, not a second heading** (`dashboard.html` keeps the page's `h1`); the **size belongs to the span and `truncate` to the wrapping link**, since `text-overflow` does nothing on an inline span and the phone's bar is the narrow one. Never retype the cream/white pairing in a template.
- Sidebar label wording is user-facing and tested by string: the progress board is **Group Progress**, the allocator button is **Simulate Allocation** (not "Calculate Allocation") and its running state is "Simulating…", and the plan's commit button is **Apply Allocation** with the count moved into a badge. Technical Drawing Allocation has a working view but no sidebar link.
- Style form widgets with the existing `INPUT_CLS` / `SELECT_CLS` constants in `core/forms.py`. Session create/edit uses the inline `SessionGroupFormSet`; the shared-course form uses `CourseRequirementFormSet` (same pattern).
- The **shared courses** resource lives at `/course-requirements/` (URL names `course-requirement-*`, sidebar label "Courses" under Reference Data) and keeps the standard 5-view CRUD shape, so it reuses `core/list.html` / `core/_table_and_cards.html` / `core/_detail_content.html`. Its list rows are real `Course` instances with the computed columns attached as instance attributes by `_course_row` — the shared table partial resolves columns with the `get_attr` filter, so a plain dict renders every cell blank.
- The allocation page is **not** a list view. It posts to `/allocation/preview/`, `/allocation/apply/`, `/allocation/revert/`, `/allocation/assign/` and `/allocation/unassign/`, each of which answers an htmx fragment or a plain `redirect()`. Feedback goes out as an `allocation-toast` `HX-Trigger` (the listener is in `base.html` next to `import-toast`); the fragment is `core/_allocation_message.html` plus `core/_allocation_plan.html`. The plan template reads **only the snapshot dict**, never a live `AllocationPlan` — a fresh run and a reloaded saved run then render identically.
- **The plan is presented twice, and the page must never be the thing that scrolls sideways.** `core/_allocation_plan.html` renders each of its three tables as a labelled card list (`.tt-plan-mobile … lg:hidden`) *and* as a table (`.hidden lg:block overflow-x-auto`). Nine columns cannot be read at 375px, and a nine-column table is why `/allocation/` used to be wider than the screen. Each view carries **every** field of the other, so the card list is not a summary that quietly drops capacity or the change status; each is hidden at the other's breakpoint, so exactly one renders — the same duplication contract as the timetable grid/agenda pair, including the consequence that **"this text appears once" must be asserted against one view**, not page-wide.
- **A grid/flex item needs `min-w-0` before an `overflow-x-auto` descendant will scroll instead of widening the page.** Default `min-width: auto` lets a wide child stretch the track, so `overflow-x` on the *child* never engages and the whole document scrolls. The wrapper, the `#allocation-plan` fragment and the two-column grid in `allocation.html` all carry `min-w-0` for that reason; `GroupProgressBoardTests` and `AllocationPageTests` assert the wrapper class. This is the same trap as the programme-timetable group's progress column: constrain the widest cell (`max-w-[16rem]` + `break-safe` on the board's "Still needed" list) rather than only wrapping the container, or the table is still miles wider than a phone.
- **An applied run is visible everywhere, because allocation only ever writes `SessionGroup`.** Nothing downstream needs to know allocation exists: the sessions list, the session detail panel, the on-screen timetable, `collect_group_entries` / `collect_entries` / `collect_master_entries` and all three PDF exports read those same links. `/sessions/` annotates each row with `assigned_groups` and `allocatable` via `_annotate_sessions` (also called from `session_detail`, or the detail panel renders them blank) and offers an `?assigned=no` filter plus a count of unassigned small-group sessions — the working view for deciding what to allocate next.

## Timetable view & PDF exports

- On-screen timetable (`/timetable/`, view `timetable_view`) and the PDF exports both build on `core/timetable_pdf.collect_entries` (sessions + workshops + TDs for a programme, or `collect_group_entries` for a single group). The on-screen view uses `core/timetable_grid.build_day_time_grid` (DAYS as rows — always the full Monday..Friday range with full weekday labels, plus any weekend days present; hourly TIME columns each labelled in the master-timetable format e.g. `07:00-07:55` — on-screen slot labels are built by `_screen_slot`, while the PDF/classic grid keeps the plain `07:00-08:00` labels from `_slot`). Each day is a vertical band of sub-rows (lanes, `_partition_lanes`): a session that spans several hourly slots is drawn as ONE cell merging those columns (`colspan` derived from every covered hour, including partial hours), and overlapping sessions sit on separate lanes instead of being sliced into one box per hour column. Rendered through `templates/core/_timetable_grid.html` with one plain-text entry box (`templates/core/_activity_card.html`) per entry — the box reads exactly like the UDSM Excel grid cells: `"Type, Start-End, Day"` / `Course: CODE` / `Venue: VENUE` / `Assigned groups: GROUPS`. **The groups line is drawn in blue (`class="tt-line groups"`, the on-screen twin of `GROUPS_STYLE`) and is omitted entirely for a lecture** (`{% if entry.kind != "lecture" %}`) — a whole-cohort lecture is not "assigned" to anyone, so it neither prints a group list nor an empty line. For a session with no groups the line is present but blank. The master timetable entries are the source of truth: ungrouped sessions still appear.

### The on-screen grid and the mobile agenda

The grid is **uncapped and fluid**: `#tt-page` in `templates/core/timetable.html` is `width: 100%; max-width: none` (never re-add a `max-w-*` wrapper), and `_timetable_grid.html` feeds real column minimums to a `<colgroup>` as `--tt-day` / `--tt-hour` / `--tt-slot-count`, using `min-width: calc(var(--tt-day) + var(--tt-hour) * var(--tt-slot-count))` as the *overflow floor* — the table therefore grows into whatever the sidebar leaves instead of stopping at a fixed width. `html.tt-collapsed` widens the share the grid can claim, which is the whole point of collapsing the sidebar. Typography and row height step at breakpoints, the time header row and day column are sticky, and the scroll container gets edge shadows plus `role="region"`.

**Narrow screens get an agenda, not a squeezed table.** `templates/core/_timetable_agenda.html` renders `row["entries"]` — a chronological per-day list that `build_day_time_grid` now attaches to each day row alongside `lanes` (`_chronological`, ordered by earliest covered hour, then start time) — reusing `_activity_card.html` so a session is described by one box format in both views. **The two views duplicate every card in the served HTML**; the agenda is `display: none` above the mobile breakpoint and `.tt-agenda { display: none !important; }` in print, so nothing is shown twice on screen or on paper. Consequence: any "this text appears once" assertion has to be scoped to one view (split on `class="tt-agenda`), not counted page-wide. The PDF exports use `core/timetable_grid.build_time_day_grid` (TIME rows / DAY columns, merged via `rowspan`). DAYS-only filter on `Day` choices; fills via `fill_color`; PDF rendering is `render_programme_timetable`/`render_group_timetable` (reportlab `SimpleDocTemplate` — the on-screen/template shading matches the PDF colours).
- Export URLs: `export/` (export picker page), `export/programmes/<pk>/timetable.pdf/` (name `programme-timetable-export`), `export/groups/<pk>/timetable.pdf/` (name `group-timetable-export`); also `programmes/<pk>/timetable.pdf/` (`programme-timetable-pdf`), `timetable/` (`timetable`), `timetable/groups/` (`timetable-groups`).
- PDF exports accept `?semester=<pk>` & `?year=<n>`; without `semester` they fall back to the latest semester that actually has data (`_latest_semester_with_data` in `core/views.py`).

### The workshop rotation key and the export footer

- **The rotation key is exactly three columns — Weeks, Group, Workshop — and one row per distinct (week block, workshop) pair.** Rows are **shared, never repeated per group**: whole programmes rotate on one schedule, so printing C1's weeks and then C2's says the same thing twice. Groups on the same schedule are collected into one row and the Group column lists them, compacted through `_compact_group_codes` (`EE C1, C2, CE A1`). Only a genuinely different schedule earns its own row. Rows are ordered by week number then workshop name, via `_week_sort_key` — **never order on the label text**, since "Week 15-21" sorts before "Week 8-14" as a string and a three-way rotation reaches a two-digit week.
- **The group export's workshop cell carries no week range** (`show_week_notes=False` → `build_grid` → `time_day_grid_to_table` → `cell_markup`). A folded workshop cell states only type, time and groups — the workshop *names* never appear there at all — so a range beside it is unreadable, and the key below states the mapping properly. The **programme export keeps the range** (`show_notes=True`): there two groups doing the same workshop in the same slot but different week blocks collapse into one cell, and the range is the only thing telling them apart.
- **The week range is part of a block's identity in `fold_same_sessions`.** The bucket key is `(slot, identity, note)`. Without it, two entries differing only by week range merge and the cell keeps the *first* entry's note — printing "ALL groups, weeks 1-7" and being wrong about everyone else. Equal ranges still fold, which is the common case.
- **All three exports share one footer.** `_draw_master_footer` takes the page size from `doc` (never hardcode `landscape(A4)`) so the portrait grid sheets get the identical strip, and it is painted on the canvas via `onFirstPage`/`onLaterPages` so it repeats on **every** page at the bottom margin. It used to be a flowable appended to the element list, which put it wherever the content ended — near the top of page one for a short timetable — and nowhere else. The two grid views pass `portal_url=request.build_absolute_uri("/")` like the master view; the test asserts the `Tm` y coordinate is under 60pt, which is the only honest way to catch a footer that is present but in the wrong place.

### Folding duplicate sessions (all PDF exports)

`fold_same_sessions(entries)` in `core/timetable_pdf.py` is the single place the "same day + same time + same course is one session" rule lives; `fold_for_display(entries, all_group_codes, show_groups=True)` adds the group list and cell text on top. **All three PDF exports call it** (`render_udsm_master_timetable` via `_merge_master_entries`, plus `render_programme_timetable` and `render_group_timetable`); the on-screen timetable view deliberately does **not** yet, so `collect_entries`/`collect_group_entries` still return one entry per group there.
- **A single group's own export draws no assigned-groups line.** `render_group_timetable` passes `show_groups=False`, which leaves the line out of the cell text while still computing it on the entry, so a caller that wants the data still has it. On that sheet the reader already knows whose timetable it is, so printing the group back to it is noise — worse, a whole-cohort lecture would read `ALL`, because that one group genuinely *is* every group on the sheet. The other two exports are unaffected and keep their groups line.

- **A slot is a day plus the set of hours covered — not the clock strings.** `_slot_of` keys on `frozenset(entry["hours"])`, which is what lets a `09:00-12:55` placeholder and a `09:00-13:00` allocation be recognised as one slot. Keying on the raw `start`/`end` strings is exactly what let the two be drawn as separate blocks.
- **One daily workshop slot is ONE session, whoever attends it.** `_identity_of` identifies a workshop by its slot alone (`("workshop", "")`), not by which craft it is, so Carpentry + Welding + Masonry at Monday 09:00-13:00 collapse into a single block reading `Workshop` with every attending group listed. Splitting them per craft was tried and rejected: it turned one session into three and buried the group list. Technical drawing keeps its course, so two genuinely different TD courses in one slot still read separately.
- **A placeholder course code names no course.** `PLACEHOLDER_COURSE_CODES` covers `WORKSHOP`, `TD`, `TECHNICAL DRAWING` and friends; such a session is dropped when allocations actually describe its slot, and **kept** when they do not (dropping it would silently lose a real class).
- **An `ME101` practical and the `ME101` technical drawing are one session.** A session whose course a technical-drawing allocation already covers in the same slot folds into that block. Note the asymmetry: workshop coverage is slot-wide (`has_workshop`), while TD matches on course (`td_courses`).
- **Two different session courses in one slot are never merged.** For reference, the master block count went 200 → 226 while per-craft workshop splitting was briefly in place, and back to ~194 once workshops went slot-wide.
- **The assigned-groups line is emphasised: blue, bold and italic.** `GROUPS_STYLE` in `core/timetable_grid.py` is the single source (`#0b4f9e` on `Helvetica-BoldOblique`). The line is identified **by matching the entry's own `groups` value**, not by assuming it comes last, so it survives reordering and works for a session (groups inside its label), a technical drawing (same) and a workshop (groups appended as its own line). `ALL` counts as a group list. The master export draws line by line with `drawString`, so `_pack` carries an `(is_groups)` flag through wrapping; the classic exports go through `cell_markup()` / `time_day_grid_to_table(..., markup=True)`, which is why `_cell_markup` is gone -- markup is now built already-escaped and must **not** be escaped twice.
- **`_master_cell_text` delegates to `_entry_lines`.** It used to carry its own copy of the field order and silently drifted (it kept omitting the workshop time). Do not reintroduce a second implementation of the cell text.
- **Every block states its time, workshops and technical drawings included.** `_time_span` gives `08:00-11:00`; a period-only workshop from the raw matrix workbook has no clock times of its own, so no line is invented for it. A merged workshop or TD block drops the venue and course (they would swamp the cell) but keeps type, time and groups, in the same order as a taught session.
- **A whole-cohort LECTURE reads `ALL`.** `_WHOLE_COHORT_LECTURES` is `CL111`, `MT161`, `MT171`, `ME101`, `SC121`, and `_WHOLE_COHORT_LECTURE_PREFIXES` is `("DS",)`, covering `DS114`, `DS115`, `DS115_COET` and any other DS course. **Lectures only** -- these same courses run per-group tutorials and seminars (CL111 alone has ~24 seminars) which must keep naming their own groups, so `_is_whole_cohort_lecture` checks the activity type as well as the course code. `ALL` is drawn as the groups line and emphasised, not left implicit. A lecture with no `SessionGroup` links at all still reads `ALL` rather than a blank line.
- Merging is by first-seen order and never reorders the week. Groups are de-duplicated in first-seen order and rendered compacted (`_compact_group_codes`), or as `ALL` when they cover every known group.

### All-programmes (master) export

`export/all-programmes/timetable.pdf/` → `render_udsm_master_timetable` builds a **different** layout from the two grid exports above: **A4 landscape**, one horizontal band per weekday stacked down the page, each band a narrow day-label column plus one column per printed hour. The bands are hand-drawn by `_DayFlowable` (a `Flowable`), not by a reportlab `Table`. A3 was tried and rejected: 1191pt of width for thirteen short hour columns meant the reader had to scroll sideways at 100% zoom. Keep the page at A4 landscape and the grid within the 8mm side margins.

- **Blocks are packed, not gridded.** `_pack` lays blocks down in `_stack_order` order (shortest session first, then start time) and drops each onto the *lowest* position free across every hour column it covers — including down into a hole left by a narrower neighbour. The narrow blocks therefore keep the top of the band, the wide ones sink into the gaps, and the band is as short as the data allows. Never overlap: the placement test is exact, and `test_boxes_never_overlap_within_a_day` guards it.
- **`BLOCK_GAP` is reserved by the packer, not faked by the renderer.** `_lowest_free` offers `run_top + BLOCK_GAP` as candidate positions and records occupancy as the plain logical span `[top, bottom]`, so a packed block's drawn rect *is* its logical box and the gap you see between two stacked sessions is exactly `BLOCK_GAP`. Drawing the box inset vertically as well would halve the visible margin — the inset is horizontal only, keeping blocks off the column lines. Each band also carries a trailing `BLOCK_GAP` margin (`height = content_height + BLOCK_GAP`), which is what puts the same clear space between the last block of one day and the first block of the next.
- **One rule per band, in the middle of that margin** (`RULE_WIDTH`, drawn at `rule_y = margin / 2`). Consecutive bands carry no spacer, so that single rule separates two days — one line, equal clear space either side, no gutter, and no band ever hangs open-ended. A band's top edge is closed by whatever sits above it (the neighbouring day's rule, or the hour header painted by `_draw_master_header`, which sits flush on the frame top so it also closes the first band on each page). At a page-break seam the margin can be squeezed to zero, and `rule_y` follows it to 0.
- **A day fills the page it starts on.** `split` walks the candidate cut lines (always some block's own `top`) lowest first and takes the highest one that fits `avail_height`, so a day starts on a partly-used page instead of jumping to the next one. Returning `[]` (not `[self]`) when not even the first block fits is what makes reportlab carry the whole day to a fresh page; returning `[self]` there raises `Splitting error`.
- **A cut line may cross a block — but only in a column nothing else shares across the break.** `_clean_cut_levels` yields the lines where, in every hour column the line actually crosses, the lowest block above ends before the highest block below begins. The tempting stricter rule ("no block is crossed at all", i.e. `content <= level`) is wrong: a densely packed day is a *staircase* where the tallest block in every prefix runs past the next line, so NO line qualifies, the day gets no split at all, and it jumps to a fresh page with the space below left empty. Do not reintroduce that rule. Two related traps: a column the line does not cross is irrelevant (a lone block may span the break), and a rejected line must `continue`, never `break`, because a higher line is often clear.
- **A day's name is written exactly once, on the chunk holding the day's vertical midpoint.** Ownership is settled in `split` and handed straight down via `label_here`: a chunk that does not own the name must pass `False` to *both* children (`self.label_here and not first_owns` for the continuation — plain `not first_owns` re-grants the name and writes it twice). `_label_offset` clamps the midpoint into the chunk's content, so a midpoint landing in the clear space at a seam still sits against the blocks. Every chunk keeps its own bordered day-label column, so a day carried over from the previous page never looks cut off down its side.
- **Cell metrics** (`CELL_SIZE`/`LEADING`/`PAD_Y`): 6.5pt text at 1.26x leading — 6.5pt matches the classic A4 export, and the leading is deliberately loose so a session's fields read as separate lines. Margins are sized to `HEADER_MARGIN`/`FOOTER_MARGIN` so the frame starts directly under the hour header and ends directly above the footer.
- **Header and footer are painted on the canvas**, not added to the element list, so both repeat on every page. `_draw_master_footer` writes `Generated from <portal> on <date>` with the portal name as a live link (`portal_url`, passed by `all_programmes_timetable_pdf` as `request.build_absolute_uri("/")`) plus `Page N`. A `Link` annotation lives in the page object, not the content stream, so test for it with `/URI (`, not by searching decoded text.

## Group allocation (seminar / tutorial / practical)

`core/group_allocation.py` owns every decision about which group attends which session. It holds no views or templates, so the coordinator page, the manual-assignment form and the tests all call the same functions. Page: `/allocation/` (`allocation_page` → `templates/core/allocation.html`), URLs `allocation-preview` / `-apply` / `-revert` / `-assign` / `-unassign`. Workshops are **not** allocated here, but they are read when a group's availability is computed.

- **Groups count as 30 students** (`STUDENTS_PER_GROUP`). Required capacity is `groups × 30`; a group is never split. There is no special minimum for seminar venues — a seminar gets exactly the same capacity check as a tutorial.
- **One validator, two callers.** `validate_assignment(group, course, session, semester, index, group_count_after=…)` is the single path. The engine calls it per candidate; `validate_manual_assignment` / `manual_assign` call it for the one pair the coordinator typed, so a hand-made assignment can never be one the engine would have rejected. The three checks are independent and each can veto: `check_eligibility`, `check_availability` (via `AvailabilityIndex`) and `capacity_status`.
- **A missing venue and a capacity of 0 both fail.** They are `no-venue` / `unknown-capacity`, never "plenty of room" — assuming capacity would silently overfill an unverified room. Both messages tell the coordinator to fix the venue.
- **Availability is interval overlap**: `start < existing_end and end > existing_start`. `AvailabilityIndex` folds four sources together — existing `SessionGroup` links (lectures included), `WorkshopAllocation`, `TechnicalDrawingAllocation`, and the run's own proposals as it places them. Workshop and TD records name a bare group code, so they block every group carrying that code, matching the exports.
- **A technical drawing of the candidate's own course is not a clash — the two are one class.** `conflicts_excluding` skips a `td` block whose normalised course equals the candidate session's, so an `ME101` technical drawing 10:00-13:00 never blocks the `ME101` tutorial 10:00-12:55. **This has to match `fold_same_sessions`, which already merges them into a single block on every export**; if the allocator calls that a clash it refuses a session that is not a second commitment, and the group can never be placed. Note the asymmetry the export also draws: the match is **on course**, so a `TD201` drawing in the same slot is a different class and still clashes, and a **workshop always clashes** whatever its course — a workshop is its own class, and `fold_same_sessions` only folds a *placeholder* session into a workshop slot, never a real taught one. `BusyBlock.course` carries the normalised code; the block label keeps the "Technical drawing ME101" wording for the message.
- **A workshop with a day but no resolvable time blocks that whole day** and is reported as `unverifiable`. `_workshop_window` uses explicit clock times first, then resolves the Morning/Afternoon period through `core.workshop_times` — the project's own rules, not a re-implementation. Data that cannot be checked is never quietly accepted.
- **The search is one DFS over the whole requirement list, in stage order** — seminar, then tutorial, then practical, most-constrained-first inside a stage, ties broken on `course.code, programme.code, group.code, ordinal` so identical input gives identical output. Earlier stages are *not* frozen: a later stage that cannot be satisfied makes the search backtrack and try a different seminar or tutorial. When a requirement cannot be placed at all it is recorded as `Unresolved` with the specific reason and the search carries on, so a run always returns the best plan it can rather than nothing.
- **Reaching `DEFAULT_NODE_LIMIT` is reported, never called impossible.** `_SearchLimit` unwinds the DFS, `plan.search_limit_hit` is set, and the warning says in as many words that this is the best found so far, not proof that no valid allocation exists. `plan.is_complete()` is False in that case.
- **Soft preferences are only ever consulted for candidates that already passed validation**, as the tiers of `_rank_candidates`: keep a valid existing link, balance group counts, avoid gaps / a concentrated day, combine groups from different programmes. **The candidate order is re-derived each time a requirement is reached** (`try_place`), not ranked once up front: tiers 2 and 4 read the current occupancy, so ranking against a pre-placement snapshot makes "balance" a no-op and stacks every group into the lowest-numbered session.
- **Statuses are `added` / `retained` / `moved`, resolved per (group, course, activity) in `_resolve_moves`.** A retained link is *not* recorded as a change, so a revert never touches a link the run did not create. A pre-existing link that the plan does not use is reported as a warning and left in place — pruning links the coordinator did not ask about is not this feature's job.
- **Valid assignments apply while items are unresolved.** `save_plan` stores the plan and one `AllocationChange` per add/remove; `apply_run` writes the links in one transaction; `revert_run` first checks that every link is still in the state the run left it in and aborts with the conflicts listed if any drifted, so a later manual edit is never overwritten. The plan JSON snapshot (`AllocationPlan.snapshot`) is what the review template renders, so a saved run and a fresh one look identical.
- A `Session.course_code` is matched to a `Course` by normalised code. A session naming an unknown course is reported (`unknown-course`), never guessed at.

### Per-group progress and guided manual placement

Two read-only-ish pages on top of the same engine, so the coordinator can see how far each group has got and place one by hand. Both live in `core/group_allocation.py` (no new decision logic) and both judge every candidate with `validate_assignment` — the guidance can never offer a session the allocator would refuse.

- `group_statuses(semester, scope, groups)` → `{group_pk: GroupStatus}`, built from one `build_requirements` call plus one `AvailabilityIndex`. `GroupStatus` exposes `met` / `total` / `outstanding` / `percent` / `is_complete` / `state` / `activity_progress()`; each entry is a `RequirementStatus` with `assigned` and a list of `SessionOption`.
- **`is_complete` means finished, never "nothing was asked"** — a group whose courses have no requirement is `state == "none"`, `is_complete` is `False`, and the board still shows it (`has_nothing_to_do`). A coordinator must never read "100%" as success when the denominator was 0.
- **A requirement is met only by an existing `SessionGroup` link** to one of its candidate sessions. Nothing infers "satisfied" from the timetable.
- **"Free" and "valid" are separate verdicts on `SessionOption`.** `free` is "the group's timetable does not clash"; `ok` adds eligibility and capacity. A session in a 30-seat lab the group *could* attend is reported as free but not ok, so the coordinator sees a room-size problem rather than a phantom timetable clash — this is exactly the state real data gets stuck in. The current placement is not re-validated (it is the status, not a proposal) and always sorts first.
- **Already-placed requirements stay editable.** Each met entry shows the placed session with a `Remove` button, plus a collapsed "Move it: see the other sessions" toggle (Alpine `x-data`/`x-show`) carrying the same option list. A placement can therefore be moved or cleared by hand without running the allocator.
- Pages: `/allocation/groups/` (`allocation-groups` → `core/allocation_groups.html`, the progress board, sidebar entry "Group Progress") and `/allocation/group/<pk>/` (`allocation-group` → `core/allocation_group.html`). The assign/unassign buttons post to the **existing** `allocation-assign` / `allocation-unassign` endpoints — there is no second write path. Candidate rows are shared between the two states in `core/_allocation_options.html`; do not fork the markup.
- **A placement updates the page in place, so the mutation answers with the panel, not a message.** The requirement list is `core/_allocation_group_panel.html` (root `id="allocation-requirements"`, swapped with `outerHTML`), rendered on its own by `/allocation/group/<pk>/panel/`. The forms send `panel=1` plus **the semester and scope they are looking at** (`core/_allocation_view_fields.html`); without those the endpoint resolves "the semester" itself and silently redraws the list against a *different* set of sessions the moment the coordinator clicks. When a `panel` post names no semester, the session being placed names one outright — use that rather than picking the latest. A non-htmx `panel` post redirects back to the group page, because there is no htmx to swap bare markup into. Without `panel=1` the same endpoints still answer with `_allocation_message.html` for the allocation page's own form, so keep that path.
- **Board rows sort most-finished first** (`state != "complete"` as the leading key — plain `state == "complete"` sorts the done groups *last*). `nav_section` needs the specific `allocation-groups` / `allocation-group` prefixes *before* the generic `allocation` entry, because the lookup returns on the first match and the generic one would otherwise light up the allocator link.
- **The board is a swappable fragment, and a row is the way into the group.** `core/_allocation_groups_board.html` (root `id="allocation-groups-board"`, `hx-trigger="refresh from:window"`, `hx-swap="outerHTML"`) holds the summary tiles *and* the table, and `allocation_groups` serves it on its own for an htmx GET — the same split `list.html` / `_table_and_cards.html` make, so a redraw can never disagree with a fresh load. Each `<tr>` carries `hx-get` to `/allocation/group/<pk>/slide/` (`allocation-group-slide` → `core/_allocation_group_slide.html`, which *includes* `_allocation_group_panel.html` rather than forking it) plus `@click="slideOpen = true"`, so a tap anywhere opens the group in the shared slide-over; the trailing "N to place" link stays and is `@click.stop`ped so it still navigates. `slide_url`/`board_url` carry the board's own `?semester=&scope=` — never let the panel resolve the semester itself. Because a placement made from that panel changes the row behind it, `_panel_response` fires `refresh-table` alongside `allocation-toast`, and `base.html`'s handler triggers the board as well as `#data-table-wrap`. On a phone the **Programme** column is `hidden md:table-cell` and **By activity** is `hidden sm:table-cell` — scoped away, never removed; the panel names the programme and lists every requirement.

## Data model / importers

- `core/importers.py` returns an `ImportResult` (created/updated/skipped/errors/conflicts, plus reconciliation fields). All importers are header-flexible: `_match_col` matches columns case/punctuation-insensitively against per-importer alias lists (e.g. `course_code`/`course code`/`course`, `venue`/`room`, `capacity`/`seats`, a single `time` range column such as `09:00-12:00` is split via `_split_range`). Missing *required* columns are reported once with the actual headings found. Master-timetable import (`reconcile_master_timetable`, `import_master_timetable_from_excel`) is idempotent, requires a valid `Semester` passed explicitly (blocks with a clear error when `semester_id` is `None` — it is never guessed), auto-creates missing venues with capacity 0 on real imports (not dry-run), expands the legacy group code `ALL` via `ProgrammeCourse`→programme→`StudentGroup` (unresolvable ALL rows become conflicts, never silently dropped), reports missing courses/groups/venues, and after writing (real import only) automatically attaches every programme group that studies the course to each LECTURE session via the shared `assign_lecture_groups(semester)` helper (same as the manual "Assign Lecture Groups" action on the sessions list; counts land in `result.lecture_sessions_processed`/`lecture_groups_linked`/`lecture_groups_existing`/`lecture_skipped_courses`). Comma-separated course codes in one cell are split into separate sessions (`_split_csv`); comma-separated venues are NOT split (kept verbatim as the venue name). The web upload form asks for the target semester for master-timetable (`"semester": "required"` in `IMPORT_TYPES`) and makes it optional (auto-detect) for workshop/TD. Workshop/TD imports use `update_or_create` on a full natural key with `defaults={}` so re-imports are no-ops. All session/workshop/TD imports target a `Semester` by PK (`--semester`); `None` means auto-detect (workshop matrix from the workbook title — auto-creates the detected semester when missing; flat files fall back to semester 1). `import_programme_courses_from_excel` resolves the programme by code then exact name, and auto-creates a missing programme from its full name (`_derive_code` builds a code from significant-word initials, e.g. `BSc. in Chemical and Processing Engineering` → `CPE`; numeric suffix on collision), reported via `result.programmes_created` (rendered on the import result panel). `import_td_allocation_from_excel` also accepts the pivoted Day/Time/Group/Venue layout: day/time/venue are forward-filled over merged-cell blocks (`_fill_down`) and a `time` range is split; a `course_code` column is still required (clear error otherwise).
- **Requirements can be derived from the timetable**, and that is the normal path for a fresh database — the coordinator's own programme-course workbook has no requirements column. `import_master_timetable --derive-requirements` (or the matching checkbox on the web upload) reads the sessions it has just imported and sets each course's requirement from them: `CL111` with only SEMINAR sessions gets `Seminar`, `ME101` with TUTORIAL *and* PRACTICAL gets both. The rule lives in `core.group_allocation.derive_requirements_from_sessions` and is shared with `set_course_requirements --from-sessions`, so the command and the import can never disagree.
  - Two rules keep the guess honest. **Only an activity that has a session is ever set**, so the derivation cannot invent a requirement nothing in the timetable could satisfy — a course whose tutorials are not timetabled yet is left alone rather than promised a tutorial. And **a course that already has a requirement is never overwritten**: the programme-course workbook's column, or a value someone set by hand, is a decision, and re-running an import must not quietly replace it (it is listed in `result.derived_skipped` instead).
  - A course with no small-group session at all is listed in `result.derived_unresolved` with a reason, never silently given a blank requirement — "needs nothing" and "we could not tell" are different things, and only the first is a decision.

- **`import_programme_courses_from_excel` also populates the shared `Course` records**, from an optional requirements column. Three things it must never do: silently ignore a requirements column, silently read a count as 1, or silently pick a side in a conflict.
  - **Column resolution** is `core.group_allocation.find_requirements_column`, layered most-confident-first: an explicit `--requirements-column`, then `REQUIRED_ACTIVITIES_ALIASES` ("Required Activities", "Allocation Requirements", "Alloc Requirements", "Activities Required", "Required Sessions", …) matched on letters+digits only, then a fuzzy pass pairing a requirement word (`required`/`req`/`alloc`) with a noun for the thing required (`activit`/`session`/`class`/`contact`/`requirement`) which catches "Allocated Activities". Whatever is left over is returned as `unrecognised` and reported as an **error** — that is the fix for the worst failure mode, where a whole file's requirements quietly do nothing. Activities in headers are matched **on word boundaries against the original text** (not the squashed key), otherwise `Semester` matches "sem" and every workbook reports a phantom column.
  - **Separate count columns** are supported too: `find_requirement_count_columns` claims a header that names **exactly one** activity plus a count word ("Tutorial Count", "Number of Practicals", "Tutorials per week"), and those counts *add* to the combined cell so the two layouts can be mixed in one file. Exactly-one is what stops "Required Activities" being read as three counts.
  - **Cell parsing** is `parse_requirements`: it unescapes HTML, normalises unicode dashes, splits on `; , / | • + &` and newlines, then for each token takes **one** count (leading digits, a leading spelled-out number, `x2`, a trailing bracketed number, a trailing bare number) and matches activities anywhere in what remains — so "Practical (2)", "Two practicals", "Tutorials per week: 2" and an unseparated "Seminar Tutorial" all read correctly. `format_requirements` is the exact inverse and there is a round-trip test over every shape. A cell that is understood but cannot be applied always yields a problem, never a wrong count.
  - **No requirement stated** is a value, not an error: `-`, `N/A`, `none`, `not required`, `no allocation`, `TBC` and friends map to "no allocation required" and produce no problem (`_BLANK_CELLS`). That is a materially different thing from `Fieldwork`, which is an unrecognised value and is reported per row into `result.invalid_requirements`, leaving that course with **no** requirement set (never fatal — the programme link is still written).
  - Re-import is idempotent, which required two rules in `_sync_course`: **only the first row of a code writes anything** (a workbook repeats a course per programme), and **a blank cell is "no opinion", not a conflicting value** (a blank requirements column must not wipe what someone set by hand). Two *different stated* names or requirement sets for one code are reported as `result.conflicts` and the stored value is left untouched — picking a side there would be the silent resolution the spec forbids, and would make every re-import flip the name. The losing name spellings are kept in `Course.name_variants`.
  - The result panel shows which column was read (`result.requirements_column`), which count columns, a per-row `course_requirements` table, `warnings` for a workbook with no requirements column, and `invalid_requirements` — so the coordinator can verify the parse instead of taking it on trust.
- Workshop import accepts BOTH formats based on a content sniff (`core/workshop_parser.py`): the legacy flat columns (`course_code, group_code, day, start_time, end_time, venue`) and the raw university Workshop Schedule matrix workbook (GROUPS/POSITION/SCHEDULE/KEY layout) parsed by `parse_workbook` → `WorkshopRecord` intermediates (`reconcile_workshop_workbook` = dry preview; `import_university_workshop_workbook` = write, `--dry-run` supported). The flat importer accepts TWO flat layouts detected from the headers: FORMAT A (`course_code, group_code, day, start_time, end_time, venue`) uses the provided course_code; FORMAT B (`group_code, day, start_time, end_time, venue`) derives `course_code` from the venue cell (e.g. `Electrical` → course_code `Electrical`); blank course_code cells in FORMAT A fall back to the venue too. Neither layout present → a clear `Invalid workshop format` error listing the required columns. Both are idempotent via `update_or_create` on the full natural key. The matrix read derives course_code/workshop from the workshop category, day+`time_period` from the KEY legend positions (no invented clock times → `start_time`/`end_time` are NULL), week_start/week_end from the contiguous week runs per section, and creates the referenced `Semester` from the workbook title when missing; group codes without a matching `StudentGroup` are reported, never created. Raw stray cells (e.g. `Q18=4`) land in `result.unrecognized_cells`.
- `core/models.py`: Semester (unique year+sem), Programme, StudentGroup, **Course** (one shared record per course code), **CourseActivityRequirement** (one row per configured activity, with a `count`), ProgrammeCourse, Venue, Session, SessionGroup (through M2M), WorkshopAllocation, TechnicalDrawingAllocation, **AllocationRun** / **AllocationChange** (saved, revertable runs), ActivityLog (`LogAction` choices CREATE/UPDATE/DELETE/IMPORT/ASSIGN/REMOVE), ImportHistory. Activity/day are stored as UPPERCASE `TextChoices` (`LECTURE`, `MONDAY`, ...).
- **Course codes are compared through `normalise_course_code()`** (trim, collapse internal whitespace, upper-case) — the one canonical form, used by the shared `Course.code`, by the programme-course importer on write, and by the allocator to match `Session.course_code` (still plain text) to a `Course`. Never add a raw `course_code=` comparison for new code.
- **`ProgrammeCourse.course_code` / `course_name` are mirrors, not fields you edit.** They exist so the many existing `filter(course_code=...)` queries, exports and templates keep working. `ProgrammeCourse.save()` copies them off the shared `Course`, `Course.save()` re-pushes them onto every link when the shared record is renamed, and `attach_course()` creates the right `Course` when a link is saved without one. The `ProgrammeCourseForm` deliberately does not expose them.
- A course with **no** `CourseActivityRequirement` rows requires no allocation and is reported as "requirement not configured" during allocation review — it is never silently allocated. Course codes imported under several names keep one name plus the alternatives in `Course.name_variants`; the migration that built the shared records picks deterministically (most frequent, then shortest, then alphabetical) and `manage.py check_course_requirements` lists them.
- SQLite (`db.sqlite3`, gitignored). After model changes run `makemigrations core` and `migrate`.
